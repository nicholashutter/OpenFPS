Why a generator

Before the generator, every new map meant a new XxxMapBuilder.java in tools/ — 200 to 500 lines of near-duplicate code per map. The thirteen hand-written builders (cornerstone, overpass, tripoint, refinery, foundry, …) all open a ModelBuilder, walk a fixed list of boxes, and write a .ofm. The only thing that varies is which boxes, where, and which swatch they sample.

The generator collapses that to write a JSON, run a Gradle task. A map is a config file: a flat list of primitives (boxes, signs), each with a position, a size, a submesh group, and a Kenney swatch. The generator parses the config, walks the primitives, and produces the .ofm. Two configs with the same bytes produce byte-identical output — the property that makes "checked-in, diff-friendly, reviewable in a PR" the right workflow.

Why a separate tool? Maps are data, not code. A 320-unit floor with 19 walls and 6 landmark buildings is a 25-line list of primitives, not a 400-line class. The generator is the seam that lets maps live as data while the engine still treats them as opaque .ofm bytes.

Architecture at a glance

The generator is a single Gradle subproject, a single package, nine files:

tools/src/main/java/com/openfps/tools/mapgen/ ⧉ MapGenConfig.java — the parsed, validated config ⧉ JsonConfigParser.java — JSON → MapGenConfig ⧉ Primitive.java — the interface every shape implements ⧉ PrimitiveFactory.java — type-name → PrimitiveBuilder registry ⧉ Box.java — the closed axis-aligned solid ⧉ Sign.java — the flat plane (vertical or horizontal) ⧉ KenneySwatch.java — the named swatch enum ⧉ MapGenerator.java — walks a config, produces .ofm bytes ⧉ MapGenMain.java — CLI entry point for the Gradle task

The package has one entry point (the MapGenMain CLI), one type registry (the PrimitiveFactory), and one runtime (the MapGenerator). The config schema, the primitive vocabulary and the swatch catalogue are all data, not control flow.

The lifecycle, step by step

A config file travels through five steps to become a runnable map:

1. JSON file → 2. JsonConfigParser → 3. MapGenConfig ↓ 4. PrimitiveFactory → 5. List<Primitive> ↓ 6. MapGenerator → 7. byte[] (the .ofm)
  1. Read the file. The CLI opens the path, slurps the bytes, and hands them to Gson.
  2. Parse the JSON. JsonConfigParser walks the object graph: top-level fields, then the primitives array, then each primitive's type field.
  3. Validate. MapGenConfig's constructor checks every field — id non-blank, textureEdge a positive power of two, primitives non-empty. Each primitive's validate() runs once, after construction, so a malformed object fails at parse time, not vertex-append time.
  4. Build primitives. For every primitive object, the factory looks up the type string in its registry and calls the registered builder. Two built-in types: box and sign.
  5. Generate. The generator groups primitives by (submesh, texture) pair, opens one submesh per group, calls each primitive's addTo(builder, textureIndex) in order, and serialises the model to byte[].
  6. Write the file. The CLI writes the bytes to engine/src/main/resources/maps/<id>/level.ofm, which the engine's MapScene already knows how to load.

Config schema

One JSON object, top-down. Required fields are non-blank; optional fields have defaults.

FieldTypeRequiredNotes
idstringyesStable map identifier — the --map=id string. Must be non-blank.
displayNamestringyesMenu-visible name. Must be non-blank.
settingstringnoURBAN_WARZONE / INDUSTRIAL_COMPLEX / DESERT_RAVINE / ARCTIC_STATION. Documentation; the generator does not consume it.
modestringnoTDM / HARDPOINT / DOMINATION / CTF. Same: documentation only.
textureEdgeintyesKenney tile edge in texels. Must be a positive power of two (32, 64, 128, …).
worldUnitsPerTilefloatyesHow many world units one texture repeat spans. Must be positive. Typically 8.0.
primitivesarrayyesOrdered list of shape objects. Must be non-empty.

Primitive object

Every primitive has a type field and a body that depends on the type. Two types are built in:

TypeBodyEmits
box x, y, z (min corner, floats, required)
sx, sy, sz (extents, positive floats, required)
submesh (int, default 1 = wall)
texture (string, default wall) 		12 triangles, 6 faces, two per face. UVs grow with world position so neighbouring boxes tile seamlessly.
sign cx, cy, cz (centre, floats, required)
w, h (width and height, positive floats, required)
yaw (degrees, default 0)
vertical (bool, default true)
submesh (int, default 1 = wall)
texture (string, default wall) 		2 triangles, single face. Two orientations: vertical (xz plane, normal +z rotated by yaw) for banners; horizontal (xy plane, normal +y) for ground decals and ceiling panels.

Submesh convention: 0 = floor, 1 = wall, 2 = accent. The submesh index is a design knob, not a property of the type — a future "ceiling" box can sit in submesh 1 without changing the type registry.

Full example: the POC sample config

The included tools/config/maps/sample-cornerstone.json produces a 320×320 urban three-lane map: a floor slab, four perimeter walls, two interior walls with cut-throughs, four landmark buildings, six crates, six accent red posts. 25 primitives, ~300 triangles, 4 submeshes, smoke-tests clean.

{
  "id": "sample-cornerstone",
  "displayName": "Sample Cornerstone (config-driven)",
  "setting": "URBAN_WARZONE",
  "mode": "TDM",
  "textureEdge": 64,
  "worldUnitsPerTile": 8.0,
  "primitives": [
    { "type": "box", "x": -160.0, "y": -4.0, "z": -160.0,
      "sx": 320.0, "sy": 4.0, "sz": 320.0,
      "submesh": 0, "texture": "floor" },
    { "type": "box", "x": -160.0, "y": 0.0, "z": -160.0,
      "sx": 320.0, "sy": 96.0, "sz": 6.0,
      "submesh": 1, "texture": "wall" },
    { "type": "box", "x": 72.0, "y": 0.0, "z": 100.0,
      "sx": 16.0, "sy": 56.0, "sz": 16.0,
      "submesh": 1, "texture": "crate" }
    // ... 22 more primitives
  ]
}

Run the generator on this config and the result is a 105 KB .ofm at engine/src/main/resources/maps/sample-cornerstone/level.ofm. The engine's --map=sample-cornerstone smoke test loads it, runs 120 tics, and shuts down cleanly.

Built-in primitives: Box and Sign

Box

The single most common primitive in any COD-style map. A floor slab, a perimeter wall, a landmark building, a crate — they're all boxes with a texture and a placement. Twelve triangles, six faces, two per face, wound counter-clockwise as seen from outside. UVs grow with the world position so a 320-unit floor reads as one big tiled surface rather than as a mosaic of 64-pixel squares.

The Box class is the seam the parser hands a finished value to. Code that builds a box from raw numbers uses the constructor; code that reads a config uses Box.fromJson. Both produce the same triangles.

Sign

A flat plane. Two triangles, no depth, no thickness. Useful for ceiling lights, ground decals, suspended banners, and the one-sided surfaces a hand-built map would model as a stretched rectangle of paper. A Box is too much for these — twelve triangles where two are enough, and the wasted faces are visible from below the decal or behind the banner.

A sign is anchored at its centre, with a w along the local x axis and an h along the local y axis. The plane is rotated about the world y axis by yaw and is then either vertical (default, the natural orientation for a wall) or horizontal (for a ground decal or a ceiling panel).

Two real orientations, not a general normal vector. A general normal would let callers specify things the renderer would then have to reason about (backface cull, which side is "front") and would invite near-vertical planes that read as flickering slivers. Two orientations, each with a well-defined normal, sidesteps that.

Kenney swatches

The texture field on a primitive is a name, not bytes. The generator resolves the name through a KenneySwatch enum to the right swatch coordinates in the Kenney Prototype Kit's colormap.png. If the Kenney atlas isn't staged, the generator falls back to a procedural tile per swatch, so a fresh clone still produces a runnable .ofm.

NameUse
floorFloors, large horizontal surfaces
wallWalls, vertical surfaces (the default)
accentTrim, streetlights, decorative geometry
accentRedRed accents — flag poles, side markers
accentOrangeOrange accents — warning strips, signposts
crateWooden crates, deployable cover
columnVertical columns, pillars, distillation towers

The names are registered by KenneySwatch.registerBuiltins(factory) at factory construction time. New swatches are added by adding a name to the registry — no schema change required.

Using the generator

Gradle task

The mapgen CLI is wired into tools/build.gradle.kts as :tools:buildMapFromConfig:

.\gradlew.bat :tools:buildMapFromConfig ^
  -Pconfig=tools\config\maps\sample-cornerstone.json ^
  -PmapId=sample-cornerstone

The task reads the config, runs the generator, and writes the .ofm to engine/src/main/resources/maps/<mapId>/level.ofm. The engine's MapLibrary already knows how to load any level.ofm from that path, so a fresh config-driven map is runnable with one command:

.\gradlew.bat :engine:run --args="--headless --map=<mapId> --fps=60"

CLI

The same code is reachable as a standalone CLI for ad-hoc runs:

java -cp tools/build/libs/tools-*.jar ^
  com.openfps.tools.mapgen.MapGenMain ^
  --config=tools\config\maps\sample-cornerstone.json ^
  --map-id=sample-cornerstone

The CLI prints one log line per swatch (loaded from atlas or procedural) and one line confirming the .ofm bytes were written. Errors are loud: a malformed config fails the build at parse time, not at vertex-append time.

Extending: adding a new primitive type

Adding a new shape is a three-step change in one place: the new class, one registration call, and the JSON schema grows by one type string. The generator never grows a switch and the parser never grows a new keyword outside the registry.

Step 1 — Implement Primitive

Write a new class implementing the Primitive interface:

public final class Ramp implements Primitive
{
    // ... fields ...

    public static Ramp fromJson(final JsonObject obj, final float worldUnitsPerTile)
    {
        // parse JSON, validate, return
    }

    @Override public String type() { return "ramp"; }
    @Override public int submesh() { return ...; }
    @Override public String texture() { return ...; }
    @Override public void addTo(final ModelBuilder b, final int texIdx) { ... }
    @Override public void validate() { ... }
}

Step 2 — Register it

One line in PrimitiveFactory.createDefault:

factory.registerType("ramp", (obj, wup) -> Ramp.fromJson(obj, wup));

Step 3 — Use it

The type string is now valid in any config:

{ "type": "ramp", "x": 0, "y": 0, "z": 0,
  "length": 32, "width": 16, "height": 24,
  "submesh": 1, "texture": "wall" }

That's the whole extension. The factory, the generator, the parser, the CLI, the Gradle task — all unchanged. The schema grows by one type string; the rest of the system picks it up automatically.

Why no auto-discovery? Classpath scanning would couple the generator's behaviour to whatever happens to be on the classpath at build time. A Gradle dependency added in a different module silently changing how maps are parsed is a debugging session nobody wants. The explicit registry is read in one place at one moment.

Allocation profile

The generator itself allocates:

  • One LinkedHashMap for the submesh groups — O(primitives), paid once per map.
  • One HashMap for the swatch cache — O(unique swatches), paid once per map.

No per-primitive allocation happens inside the loop beyond the ModelBuilder's growable arrays, which is the same allocation profile the existing hand-written builders have. The output .ofm is the entire budget: no scratch files, no intermediate buffers, no temporary models.
